Введение
      Архитектурные решения, которые команда разработки принимает в ходе эволюции продукта, определяют его судьбу на годы вперёд: выбор фреймворка, способ интеграции сервисов, модель данных, подходы к безопасности. Чаще всего такие решения фиксируются в чатах, рабочих переписках или вовсе остаются только в голове у автора, и со временем знание теряется: новые участники не понимают, почему система устроена именно так, а уже закрытые вопросы обсуждаются повторно. Формат ADR (Architecture Decision Record — запись архитектурного решения) решает эту проблему, однако существующие инструменты либо требуют хранить ADR в виде файлов в Git-репозитории и работать через командную строку, либо вовсе не поддерживают совместное обсуждение и управляемый жизненный цикл решений. Разработка собственного веб-приложения позволяет команде вести единую базу архитектурных знаний так же удобно, как задачи в трекере: с обсуждением, голосованием и понятными статусами.
      Цель работы: разработать функциональное и безопасное веб-приложение CADR (Collection of Architecture Decision Records — «коллекция архитектурных решений») для совместного ведения ADR внутри организаций, обеспечивающее участникам команды возможность предлагать, обсуждать и утверждать архитектурные решения через удобный веб-интерфейс, а администрации — эффективное управление участниками, ролями и настройками организации.
      Для достижения цели поставлены следующие задачи:
1. Проанализировать предметную область управления архитектурными решениями и существующие аналоги, сформировать требования к функционалу системы;
2. Спроектировать модульную архитектуру приложения и структуру базы данных;
3. Разработать серверную часть (Backend) в виде REST API на платформе ASP.NET Core (язык C#);
4. Реализовать клиентскую часть (Frontend) в виде одностраничного приложения на Blazor WebAssembly;
5. Внедрить систему разграничения прав доступа (ролевая модель: участник, архитектор, администратор организации);
6. Обеспечить информационную безопасность: JWT-аутентификацию с refresh-токенами, хеширование паролей, валидацию пользовательского ввода;
7. Провести модульное и интеграционное тестирование всех модулей системы.


1. Анализ предметной области
1.1 Описание предметной области
      ADR (Architecture Decision Record) — это короткий структурированный документ, фиксирующий одно значимое архитектурное решение: контекст, в котором оно принималось, само решение и его последствия. Формат предложен Майклом Найгардом и стал де-факто стандартом фиксации архитектурных знаний в командах разработки программного обеспечения. Традиционно ADR хранятся в виде Markdown-файлов в репозитории проекта, что затрудняет их совместное обсуждение, поиск и управление статусами: правка файлов доступна только техническим специалистам, а история принятия решений остаётся в переписках.
      Веб-приложение CADR предоставляет командам организаций единое рабочее пространство для ведения ADR: незарегистрированный пользователь может ознакомиться с возможностями системы на публичной странице, а авторизованные участники — предлагать, обсуждать и утверждать архитектурные решения. Интуитивно понятный интерфейс, разработанный по образу файлового проводника и трекеров задач, позволяет легко знакомиться с накопленной базой решений даже новым участникам команды.
      Веб-приложение может быть использовано в следующих направлениях:
* Единая база архитектурных знаний: все значимые решения команды собираются в одном месте, структурируются по папкам и связям между записями, что исключает потерю знаний при уходе участников и повторное обсуждение уже принятых решений.
* Коллективная проработка решений: любой участник организации может предложить решение, обсудить его в комментариях и выразить отношение голосом, а финальное решение утверждается либо администратором, либо автоматически по итогам голосования.
* Управление жизненным циклом: каждое решение проходит управляемые этапы — от черновика до утверждения или отклонения; при устаревании решение помечается соответствующим статусом со ссылкой на новое, сохраняя полную историю.
* Передача знаний и онбординг: новые участники знакомятся с историей решений через удобный веб-интерфейс, а экспорт утверждённых ADR в Markdown позволяет использовать накопленную базу в проектной документации и при работе с ИИ-агентами.

1.3 Требования к разрабатываемой ИС
Функциональные требования
      Веб-приложение CADR должно обеспечивать выполнение следующих основных функций:
* Регистрация и авторизация пользователей: предоставление возможности посетителям создавать учётные записи и безопасно входить в систему; опция «Запомнить меня» продлевает сессию через refresh-токен.
* Профиль пользователя: просмотр своих данных и всех созданных ADR в разрезе организаций.
* Работа с организациями: создание организации (создатель автоматически становится её администратором), редактирование и удаление, список организаций пользователя, дашборд с последними изменениями и приглашениями.
* Приглашения в организацию: отправка приглашения по email с указанием роли, принятие и отклонение приглашения адресатом.
* Управление участниками организации: просмотр списка участников, смена роли и удаление участника (доступно администратору организации).
* Ведение ADR: создание записи по выбранному шаблону (встроенному или собственному), редактирование заголовка и упорядоченных разделов, перемещение между папками, удаление.
* Жизненный цикл ADR: переводы записей между статусами («Черновик», «Предложен», «Утверждён», «Отклонён», «Требует пересмотра», «Устарел») по матрице переходов с проверкой прав, автоматическое утверждение при достижении порога голосов.
* Обсуждение решений: комментарии к ADR (создание любым участником, правка и удаление автором, удаление модератором) и голосование «за/против» с запретом голосовать за собственное решение и возможностью отзыва голоса.
* Связи между ADR: установка связей типов «связан с», «заменяет», «устарел в пользу» для отражения истории решений.
* Структурирование и навигация: иерархия папок в стиле проводника, хлебные крошки, перемещение записей и папок перетаскиванием, фильтрация по статусам, список последних изменений.
* Шаблоны ADR: управление собственными шаблонами организации с подсказками и примерами для архитекторов; защита встроенных шаблонов от изменения.
* Настройки организации: порог количества голосов «за», необходимого для автоматического утверждения ADR (значение 0 — немедленное утверждение при создании).
* Экспорт в Markdown: выгрузка отдельной записи, а также всех утверждённых записей организации единым документом.
* Ролевое разграничение прав доступа: серверная проверка прав на каждой операции; интерфейс скрывает недоступные действия, но безопасность не зависит от интерфейса.
* Обеспечение информационной безопасности: хеширование паролей, JWT-аутентификация с refresh-токенами, валидация пользовательского ввода, логирование операций.

1.4 Обоснование выбора стека технологий
      Платформа и язык программирования: C# и .NET 8. Выбор обусловлен строгой статической типизацией, высокой производительностью платформы и зрелой экосистемой для серверной разработки. C# обеспечивает надёжную основу для создания масштабируемых веб-приложений:
* Безопасность и предсказуемость. Строгая типизация и контроль ошибок компилятором (в проекте включён режим TreatWarningsAsErrors) исключают целый класс ошибок ещё на этапе сборки, что критично для системы с развитой ролевой моделью и бизнес-логикой жизненного цикла.
* Встроенное внедрение зависимостей (DI). Стандартный контейнер сервисов позволяет построить модульную архитектуру с автоматической регистрацией зависимостей и слабой связанностью компонентов.
* LINQ. Единый декларативный язык запросов к коллекциям и базе данных сокращает объём кода и количество ошибок при выборках.
* Кроссплатформенность. Приложение работает на Windows и Linux без изменения кода, что упрощает развёртывание.
      Серверная часть: ASP.NET Core Web API. Серверная логика реализована в виде REST API с модульной архитектурой: вертикальные модули (Administrations — учётные записи, организации, приглашения; Adrs — ADR, папки, комментарии, голоса, шаблоны) разделены на слои сущностей, репозиториев, сервисов и контроллеров. Дополнительно используются версионирование API (Asp.Versioning) и автоматическая OpenAPI-документация (Swashbuckle/Swagger).
      Система управления базами данных (СУБД): PostgreSQL выбрана как высоконадёжная реляционная СУБД с открытым исходным кодом. Она обеспечивает:
* Структурированное хранение данных. Реляционная модель идеально подходит для логически связанных сущностей проекта: пользователи, организации, роли, ADR, разделы, комментарии, голоса, связи, шаблоны.
* Целостность и безопасность транзакций. Поддержка ACID и внешних ключей гарантирует корректность жизненного цикла записей без дублирования или потери данных.
* Возможности серверной логики. Хранимые функции (create_adr, vote_adr), триггеры и представления (VIEW) позволяют инкапсулировать сквозную логику (присвоение номеров, пересчёт голосов, автоматическое утверждение) на уровне базы данных, исключая гонки при одновременном доступе.
* Частичные уникальные индексы. Уникальность логина, email и названий проверяется только среди действующих записей, что естественно сочетается с механизмом мягкого удаления.
      ORM: Entity Framework Core 8. Подход code-first с миграциями обеспечивает:
* Единый источник истины для схемы данных: сущности C# описывают структуру БД, миграции воспроизводят её в любой среде.
* Защиту от SQL-инъекций: все запросы формируются и параметризуются автоматически через LINQ.
* Работу с представлениями и хранимыми функциями PostgreSQL из типизированного кода.
* Единый механизм аудита: даты и авторы создания и изменения заполняются автоматически в базовых репозиториях.
      Frontend-технологии: Blazor WebAssembly. Клиентская часть реализована как одностраничное приложение (SPA) на C#:
* Единый язык разработки. Компоненты интерфейса пишутся на C#, что исключает дублирование моделей и логики между сервером и клиентом и снижает количество ошибок на стыке частей системы.
* Компонентная переиспользуемость. Собственная библиотека компонентов (таблицы, модальные окна, выпадающие списки, «капсулы» статусов) обеспечивает консистентность интерфейса.
* Встроенная авторизация. Механизмы AuthorizeRouteView и AuthenticationStateProvider позволяют скрывать недоступные страницы и кнопки в зависимости от роли.
      Интеграция API и клиентской части: NSwag. Типизированный клиент C# генерируется автоматически из OpenAPI-спецификации API: контракт «портал — API» не дублируется вручную, а тот же клиент используется в интеграционных тестах.
      Вспомогательные библиотеки: AutoMapper (маппинг сущностей и моделей передачи данных), FluentValidation (декларативная валидация входных данных), Serilog (структурное логирование с отправкой в Seq), Newtonsoft.Json (сериализация перечислений строками).
      Безопасность: ASP.NET Core Authentication JWT Bearer (подписанные и зашифрованные токены доступа), ASP.NET Core Data Protection (шифрование refresh-токенов), PBKDF2 для хеширования паролей.
      Тестирование: xUnit, Moq, FluentAssertions, WebApplicationFactory (интеграционные тесты на реальном конвейере HTTP), EF Core InMemory (модульные тесты сервисов и репозиториев).
      Среда разработки и отладки: Visual Studio 2022 и JetBrains Rider, система контроля версий Git, интерфейс командной строки dotnet. Среда обеспечивает удобную работу с решением из 37 проектов: навигацию по модулям, рефакторинг, отладку и применение миграций. Локально система развёртывается как два процесса: REST API (https://localhost:7248, со Swagger UI в среде разработки) и портал Blazor WebAssembly (https://localhost:7136), а также сервер логирования Seq.


2. Проектирование
2.1. Проектирование системы
      Веб-приложение CADR проектировалось как модульный монолит — единое развёртываемое решение, внутренне разделённое на независимые вертикальные модули. Решение состоит из 37 проектов, сгруппированных в вертикальные модули и общие слои. Каждый модуль самодостаточен и может развиваться и тестироваться независимо, а при необходимости — быть выделен в отдельный сервис без изменения бизнес-логики.
      В системе выделены два вертикальных модуля:
* Administrations — учётные записи, организации, участники, приглашения, refresh-токены;
* Adrs — записи ADR, папки, разделы, комментарии, голоса, связи, шаблоны, настройки организации.
      Каждый модуль разделён на слои: Entities (сущности и конфигурации EF Core), Repositories (интерфейсы и реализации доступа к данным), Services (бизнес-логика в классах-«менеджерах»), Api (REST-контроллеры) и Pages (страницы Blazor). Сквозные компоненты (контекст базы данных и миграции, базовые репозитории с аудитом, JWT-инфраструктура, логирование) выделены в общие слои DataAccess и Common. Композиция всех модулей выполняется в хост-проекте CADR.Api посредством автоматической регистрации зависимостей по маркерным интерфейсам сборок, что позволяет подключать модули по принципу «плагинов».
      Система развёртывается как два процесса: REST API (ASP.NET Core) и портал (Blazor WebAssembly). Портал обращается к API через типизированный клиент, сгенерированный из OpenAPI-спецификации.
      Авторизация построена на JWT-токенах: токен доступа передаётся в защищённом куки-файле (или в заголовке Authorization: Bearer), а продление сессии выполняется по refresh-токену незаметно для пользователя. Права проверяются на сервере при каждой операции.

2.1.1 Определение группы пользователей
      Гость: незарегистрированный посетитель. Доступна публичная страница с описанием системы, регистрация и авторизация.
      Участник (User): участник организации. Может просматривать ADR организации и профили участников, участвовать в обсуждении — оставлять комментарии и голосовать за или против решений.
      Архитектор (Architect): может всё, что участник, а также создавать, редактировать, перемещать и удалять ADR и папки, управлять связями между решениями и шаблонами ADR, переводить записи в статус «Предложен» и возвращать их из «Требует пересмотра».
      Администратор (Admin): может всё, что архитектор, а также управлять участниками и приглашениями (в том числе менять роли), настраивать порог автоматического утверждения, изменять статусы ADR (утверждать, отклонять, отправлять на пересмотр), экспортировать утверждённые решения, редактировать и удалять организацию.
      Роли назначаются в рамках каждой организации отдельно: один и тот же пользователь может быть администратором в одной организации и участником — в другой.

2.1.2 Функциональное моделирование
      Регистрация и вход: реализованы функции регистрации новой учётной записи и авторизации с опцией «Запомнить меня»; после входа пользователь перенаправляется к списку своих организаций.
      Организации и дашборд: пользователь создаёт организацию (становясь её администратором) или принимает приглашение; на дашборде отображаются последние изменённые ADR и ожидающие приглашения.
      Проводник ADR: папки и записи отображаются в одной таблице с хлебными крошками; «капсулы» статусов показывают количество записей каждого статуса и служат фильтрами; записи и папки перемещаются перетаскиванием.
      Форма создания и редактирования ADR: выбор заголовка и шаблона, разделы предзаполняются подсказками и примерами из шаблона, поддерживаются перестановка и удаление разделов.
      Страница ADR: просмотр разделов с подсказками, изменение статуса (отображаются только допустимые переходы), голосование, комментарии, управление связями, экспорт в Markdown.
      Управление организацией (для администратора): приглашение участников по email с назначением роли, смена ролей, удаление участников, настройка порога утверждения, управление шаблонами.
      Создание базы данных для хранения данных о пользователях, организациях, ADR, папках, комментариях, голосах, связях, шаблонах и другой необходимой информации для корректной работы приложения.
      Диаграмма прецедентов (рис. 6) отображает взаимодействие между пользователями и системой.

2.2. Разработка модели базы данных
      База данных спроектирована в СУБД PostgreSQL в подходе code-first: сущности описываются на C#, а миграции Entity Framework Core воспроизводят схему в любой среде. Всего создано четыре миграции, включая миграцию объектов БД (представления, функции, триггер). Все таблицы используют UUID-ключи, механизм мягкого удаления (запись помечается датой удаления) и автоматический аудит (даты и авторы создания и изменения); уникальные индексы являются частичными и учитывают только действующие записи.

[ДИАГРАММА: ER-диаграмма базы данных PostgreSQL — таблицы Users, Organizations, UserOrganizations, UserInvites, RefreshTokens, AdrFolders, Adrs, AdrSections, AdrComments, AdrVotes, AdrLinks, AdrTemplates, AdrTemplateSections, AdrOrganizationSettings с внешними ключами]

      Основные таблицы и их назначение:
1. Users: пользователи системы (логин, хеш пароля и соль, имя, email, отметки о блокировке и подтверждении email).
2. Organizations: организации (название, описание).
3. UserOrganizations: связь пользователей и организаций с ролью участника в организации.
4. UserInvites: приглашения в организацию (адресат, организация, назначаемая роль).
5. RefreshTokens: refresh-токены для продления сессии (срок действия, полезная нагрузка для повторного выпуска JWT, отметка безопасности учётной записи).
6. AdrFolders: иерархия папок для группировки ADR (самосвязь «родительская папка»).
7. Adrs: записи архитектурных решений (сквозной номер в организации, заголовок, статус, автор, организация, родительская папка, шаблон).
8. AdrSections: упорядоченные разделы ADR (позиция, заголовок, содержимое).
9. AdrComments: комментарии участников к ADR.
10. AdrVotes: голоса участников «за/против» (уникальность пары «запись — пользователь»).
11. AdrLinks: связи между ADR (тип: «связан с», «заменяет», «устарел в пользу»).
12. AdrTemplates: шаблоны ADR (встроенные — без привязки к организации, и собственные шаблоны организаций).
13. AdrTemplateSections: разделы шаблонов с подсказками и примерами для архитекторов.
14. AdrOrganizationSettings: настройки ADR-модуля организации (порог голосов «за» для автоматического утверждения).
      Дополнительно на уровне БД созданы представления (VIEW): organization_members (участники организации с данными пользователей) и adr_summary (сводка по записям с вычисляемым счётом голосов); хранимые функции create_adr (присвоение сквозного номера записи в организации), vote_adr и withdraw_vote_adr (голосование с проверкой корректности) и триггер trg_adr_votes_recalc (автоматическое изменение статуса записи при изменении голосов).

2.3. Проектирование интерфейсов
      Проектирование интерфейса осуществлялось с учётом требований к удобству и современному дизайну. Основным требованием было создание интуитивно понятного интерфейса, знакомого пользователю по работе с файловыми проводниками и трекерами задач.
      Принципы дизайна:
1. Минимализм — чистые линии, отсутствие визуального шума, акцент на содержимом решений;
2. Интуитивность — ADR-раздел выполнен в стиле файлового проводника: папки, таблица содержимого, хлебные крошки, знакомые значки действий;
3. Доступность — адаптивность под все устройства (десктоп, планшет, мобильный) на основе сетки Bootstrap;
4. Консистентность — единая библиотека переиспользуемых компонентов (таблицы, модальные окна, выпадающие списки, «капсулы» статусов, аккордеоны) на всех страницах приложения.

Рисунок 9 - Диаграмма классов

      В процессе реализации веб-приложения CADR были разработаны модули, обеспечивающие выполнение основных функций: учётные записи и организации с ролевым разграничением доступа, ведение ADR с управляемым жизненным циклом, обсуждение решений (комментарии и голоса), шаблоны и настройки организации, а также экспорт в Markdown.
      Архитектура системы построена на основе принципов модульности и разделения ответственности, что обеспечивает гибкость, масштабируемость и упрощает поддержку кода (рис. 9). Для реализации основных функций использовались следующие подходы:
* Аутентификация и авторизация: JWT-токен со сроком жизни один час передаётся в защищённом куки-файле (флаги HttpOnly, Secure, SameSite=Strict) или в заголовке Authorization: Bearer; опция «Запомнить меня» включает refresh-токен на 29 дней, который хранится в зашифрованном виде (ASP.NET Core Data Protection) и ротируется при каждом обновлении. Пароли хешируются алгоритмом PBKDF2 (SHA-256) с индивидуальной случайной солью. Проверка прав выполняется на сервере в сервисном слое при каждой операции.
* Модуль ADR: бизнес-логика сосредоточена в менеджерах (AdrManager, AdrFolderManager, AdrCommentManager, AdrLinkManager, AdrTemplateManager), валидация входных данных — в валидаторах FluentValidation, доступ к данным — в репозиториях над Entity Framework Core. Присвоение сквозного номера записи и голосование вынесены в хранимые функции PostgreSQL (create_adr, vote_adr), что исключает гонки при одновременном создании записей и голосовании.
* Жизненный цикл ADR: матрица допустимых переходов статусов реализована в менеджере ADR (метод IsTransitionAllowed) и продублирована на клиенте только для отображения доступных кнопок; авторитетной является серверная проверка. Автоматическое утверждение при достижении порога голосов выполняется триггером на стороне БД, а моментальное утверждение при нулевом пороге — сервисным слоем.
* Папки и структура: иерархия папок защищена от перемещения папки в собственный потомок (проверка поддерева); удаление папки каскадно мягко удаляет вложенные папки и записи с предварительным предупреждением об их количестве.
* Комментарии, голоса и связи: создание комментариев доступно любому участнику организации, правка — только автору, удаление — автору, архитектору или администратору; голосование запрещает голосовать за собственное решение; связи не допускают ссылку записи на саму себя и дублирования.
* Шаблоны и настройки: встроенные шаблоны («Минимальный», «Базовый») защищены от изменения; порог голосов для автоматического утверждения настраивается администратором организации.
* Экспорт в Markdown: экспорт отдельной записи и всех утверждённых записей организации формирует документ с номером, заголовком, статусом, автором, датой создания и разделами.
* Валидация и обработка ошибок: ошибки валидации возвращаются со статусом 422 (Unprocessable Entity) и списком полей; недопустимые бизнес-операции (например, неверный переход статуса) — 406 (Not Acceptable) с понятным сообщением; отсутствие сущности — 404; нарушение прав — 403. Единые фильтры исключений гарантируют, что служебная информация не раскрывается клиенту.

      Пример реализации:
      Для иллюстрации реализации жизненного цикла ADR ниже приведена матрица допустимых переходов статусов с проверкой роли (метод IsTransitionAllowed сервиса AdrManager):

private static bool IsTransitionAllowed(AdrStatus current, AdrStatus target, Role role, bool isAuthor)
    => (current, target) switch
    {
        (AdrStatus.Draft, AdrStatus.Proposed) => role is Role.Admin or Role.Architect,
        (AdrStatus.Proposed, AdrStatus.Approved) => role == Role.Admin,
        (AdrStatus.Proposed, AdrStatus.Rejected) => role == Role.Admin,
        (AdrStatus.Approved, AdrStatus.NeedsRevision) => role == Role.Admin,
        (AdrStatus.Approved, AdrStatus.Deprecated) => role == Role.Admin || isAuthor,
        (AdrStatus.NeedsRevision, AdrStatus.Approved) => role == Role.Admin,
        (AdrStatus.NeedsRevision, AdrStatus.Proposed) => role is Role.Admin or Role.Architect,
        (AdrStatus.NeedsRevision, AdrStatus.Deprecated) => role == Role.Admin || isAuthor,
        (AdrStatus.Rejected, AdrStatus.Proposed) => role == Role.Admin,
        _ => false,
    };

      После успешного перехода применяется правило моментального утверждения: если в настройках организации порог голосов равен нулю, запись сразу получает статус «Утверждён» (метод ApplyInstantApprovalAsync):

private async Task ApplyInstantApprovalAsync(Guid organizationId, Action<AdrStatus> setStatus, CancellationToken cancellationToken)
{
    var settings = await adrOrganizationSettingsReadRepository.GetByOrganizationIdAsync(organizationId, cancellationToken);
    var threshold = settings?.LikesRequiredForApproval ?? DefaultLikesRequiredForApproval;
    if (threshold == 0)
    {
        setStatus(AdrStatus.Approved);
    }
}

3.2. Реализация интерфейсов
      Реализация пользовательского интерфейса портала CADR осуществлялась на Blazor WebAssembly с использованием собственной компонентной библиотеки поверх Bootstrap. Такой подход обеспечил консистентность интерфейса, типобезопасность и единый язык разработки с серверной частью.
      Для реализации интерфейсов применялись следующие подходы и технологии:
* Компонентная библиотека: переиспользуемые компоненты (таблицы, модальные окна, offcanvas-панели, выпадающие списки, хлебные крошки, «капсулы» статусов, аккордеоны, поля форм) собраны в отдельном проекте и используются всеми страницами, что предотвращает дублирование разметки и упрощает внесение изменений.
* Типизированный API-клиент: клиент C# сгенерирован инструментом NSwag из OpenAPI-спецификации API. Все вызовы сервера типизированы, модели запросов и ответов не дублируются вручную.
* Аутентификация на портале: при запуске портал проверяет наличие действительного токена доступа; при его отсутствии или истечении незаметно для пользователя выполняется запрос обновления токена по refresh-куке. Состояние авторизации интегрировано со стандартными механизмами Blazor (AuthorizeRouteView): страницы и кнопки, недоступные по роли, скрываются, а переход к защищённым страницам перенаправляет на вход.
* Интерактивность: перемещение записей и папок перетаскиванием (HTML5 Drag and Drop) как на папки, так и на элементы хлебных крошек; модальные окна и offcanvas-панели для приглашений и смены роли; «капсулы» статусов с цветовыми кодами и счётчиками; динамические подсказки разделов из шаблона.
* Экспорт файлов: скачивание экспортированных Markdown-документов реализовано через JS-interop.
* Обработка ошибок: компонент ErrorBoundary отображает понятную страницу ошибки вместо «белого экрана»; сообщения об ошибках API выводятся пользователю в доступной форме.

3. Тестирование пользовательского интерфейса (UI-тестирование) — проверка корректного отображения элементов интерфейса в разных браузерах (Google Chrome, Firefox, Microsoft Edge) и на разных разрешениях экрана.
4. Тестирование безопасности — проверка ролевой модели (попытки выполнения операций без нужной роли), запрета само-голосования, недопустимых переходов статусов, корректности авторизации по токенам.
5. Ручное тестирование — пошаговая проверка всех сценариев использования приложения вручную разработчиком для выявления логических ошибок и недочетов в интерфейсе.

5 Мероприятия по информационной безопасности
5.1. Возможные угрозы информационной безопасности при работе с приложением.
* SQL-инъекции: злоумышленник может ввести вредоносный SQL-код в поля для ввода данных (логин, названия ADR и папок, комментарии), чтобы получить доступ к базе данных и совершить несанкционированные операции (изменить или удалить информацию).
* Межсайтовый скриптинг (XSS): злоумышленник может внедрить вредоносный JavaScript-код в содержимое ADR или комментарии, чтобы перехватить учётные данные пользователей, перенаправить их на фишинговые сайты или изменить внешний вид портала.
* Подделка межсайтовых запросов (CSRF): злоумышленник может заставить авторизованного пользователя выполнить нежелательные действия без его ведома (например, сменить статус ADR или оставить комментарий).
* Брутфорс-атаки на аутентификацию: злоумышленник пытается подобрать пароли к учётным записям пользователей путём перебора различных комбинаций.
* Кража или подделка токенов: перехват JWT-токена или refresh-куки позволяет злоумышленнику действовать от имени пользователя; подделка подписи токена — получить доступ без аутентификации.
* Несанкционированный доступ к данным чужих организаций (IDOR): подбор идентификаторов записей и организаций в прямых ссылках с целью чтения или изменения чужих ADR.
* Недостаточная защита персональных данных: утечка или несанкционированный доступ к персональным данным участников (имена, email, логины).
* Устаревшие зависимости: использование версий платформы и библиотек с известными уязвимостями.

Администратор (Admin)	Управление участниками и приглашениями, смена ролей, настройка порога утверждения, изменение статусов ADR (утверждение, отклонение, пересмотр, устаревание), редактирование и удаление организации, экспорт утверждённых ADR

2. Безопасная идентификация, аутентификация и авторизация
      * Идентификация осуществляется по уникальному логину: уникальность проверяется частичным индексом базы данных, учитывающим только действующие учётные записи.
      * Аутентификация: проверка подлинности пользователя по логину и паролю (рис. 11). Пароли хешируются алгоритмом PBKDF2 (SHA-256) с индивидуальной случайной солью, генерируемой для каждого пользователя (рис. 34);

3. Безопасное хранение данных и резервное копирование:
      * Хранение паролей: пароли хранятся только в виде хеша с солью, исходные пароли не сохраняются и не отображаются;
      * Мягкое удаление и аудит: записи помечаются датой удаления (возможно восстановление при сбоях), каждая сущность хранит даты и авторов создания и изменения;
      * Минимизация персональных данных: система собирает только имя, логин и email участников;
      * Регулярные резервные копии: администратор регулярно создаёт резервные копии PostgreSQL (pg_dump) и хранит их на отдельном носителе.
4. Защита кода от неправомерного использования
* Защита от SQL-инъекций: все запросы формируются через LINQ и Entity Framework Core (автоматическая параметризация) либо через параметризованные хранимые функции, что предотвращает выполнение произвольного SQL-кода, введённого пользователем (рис. 36);

Администраторы управляют составом участников и ролями, приглашают новых членов, настраивают порог автоматического утверждения и утверждают либо отклоняют предложенные решения.

Листинг модуля смены статуса ADR (жизненный цикл ADR)

Код обработки смены статуса записи ADR (сервис AdrManager):

async Task IAdrManager.ChangeStatusAsync(ChangeAdrStatusModel model, CancellationToken cancellationToken)
{
    var adr = await GetAdrOrThrowAsync(model.AdrId, cancellationToken);
    var userOrganization = await userOrganizationReadRepository
        .GetByUserAndOrganizationIdAsync(model.UserId, adr!.OrganizationId, cancellationToken)
        .OrThrowIfNull(() => new AdrAccessException());
    var current = adr.Status;
    var target = mapper.Map<AdrStatus>(model.Status);
    if (!IsTransitionAllowed(current, target, userOrganization!.Role, adr.AuthorId == model.UserId))
    {
        throw new AdrInvalidOperationException(
            string.Format(ErrorMessages.InvalidStatusTransition, current, target));
    }

    adr.Status = target;
    await ApplyInstantApprovalAsync(adr.OrganizationId, newStatus => adr.Status = newStatus, cancellationToken);
    adrWriteRepository.Update(adr);
    await unitOfWork.SaveChangesAsync(cancellationToken);
}

Матрица допустимых переходов статусов с проверкой роли:

private static bool IsTransitionAllowed(AdrStatus current, AdrStatus target, Role role, bool isAuthor)
    => (current, target) switch
    {
        (AdrStatus.Draft, AdrStatus.Proposed) => role is Role.Admin or Role.Architect,
        (AdrStatus.Proposed, AdrStatus.Approved) => role == Role.Admin,
        (AdrStatus.Proposed, AdrStatus.Rejected) => role == Role.Admin,
        (AdrStatus.Approved, AdrStatus.NeedsRevision) => role == Role.Admin,
        (AdrStatus.Approved, AdrStatus.Deprecated) => role == Role.Admin || isAuthor,
        (AdrStatus.NeedsRevision, AdrStatus.Approved) => role == Role.Admin,
        (AdrStatus.NeedsRevision, AdrStatus.Proposed) => role is Role.Admin or Role.Architect,
        (AdrStatus.NeedsRevision, AdrStatus.Deprecated) => role == Role.Admin || isAuthor,
        (AdrStatus.Rejected, AdrStatus.Proposed) => role == Role.Admin,
        _ => false,
    };
